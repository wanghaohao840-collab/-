# 分布式升级：完整迁移与可回退切换设计

**日期：** 2026-09-24
**状态：** 已确认设计方向；等待书面规格复核
**适用范围：** 当前 React/FastAPI 产品从单实例 SQLite／本地文件运行，升级为 PostgreSQL／对象存储／独立 Worker，并在隔离环境完成全流程迁移后才切换生产。

## 1. 决策与边界

本文件收窄并调整[既有分布式多用户导入设计](2026-08-09-distributed-multi-user-import-system-design.md)的实施顺序，不废除其中的租户隔离、租约、fencing、幂等及单一数据权威等规则。当前产品已包含导入、问答、搜索、来源笔记、学习计划、报告等业务，首轮验收不能只证明导入任务或 PostgreSQL schema 可用。

采用**先迁移完整业务数据底座、再切生产、最后扩容实例**的路径。各阶段保持单一写入权威；不做 SQLite 与 PostgreSQL 的实时双写，也不使用多副本共享 SQLite、JSON 或本地用户目录。正式切换后的正常回退是撤回有问题的应用版本，继续使用 PostgreSQL／对象存储并保留切换后的写入；不要求无损回写 SQLite。

不在本阶段更换嵌入模型、Qdrant 索引身份或业务功能。既有设计中的取消增强、配额、公平调度、Kubernetes、负载扩容等能力可在基础语义安全所需之外后置，不作为首次完整迁移的完成条件。保留单机 `local` 模式，但它不是分布式运行的隐式降级目标。

## 2. 方案取舍

| 路径 | 判断 |
| --- | --- |
| **推荐：端到端竖切，逐级开放生产** | 先让全部已上线业务在共享数据底座上运行，以隔离迁移与回退演练决定是否切换；基础设施和业务验收不脱节。 |
| 一次完成原设计所有平台能力 | 终态完整，但首次可验收迁移被取消、配额、调度、Kubernetes 等非切换门槛延后。 |
| 先通过共享盘／粘性会话扩多个现有实例 | 无法消除进程内会话、用户写锁、嵌入式 Worker 与本地文件的权威边界，不作为生产升级路径。 |

## 3. 目标运行边界

- PostgreSQL 是用户、会话、CSRF、文档及任务元数据、History／Memory 权威状态、问答、笔记、学习、报告元数据和租约的唯一结构化事实源。会话与用户写协调不得只存在于进程内；临时助手对象可按请求重建，但不能成为跨实例状态权威。
- S3 兼容对象存储是暂存上传、正式文档和报告等持久文件的唯一事实源。本地磁盘仅存可清理的任务临时文件。版本保留能力须对实际选用的服务验证，不假定所有 S3 兼容实现等价。
- 独立 Worker 执行后台导入、问答、删除和笔记投影等需要跨实例持续运行的任务；API 进程在 `distributed` 模式不启动嵌入式 Worker。任务领取、心跳、终态及外部写入使用数据库租约、幂等标识和 fencing，失去租约者不能提交新结果。
- Qdrant 保持文档、用户和 namespace 隔离规则，作为向量数据后端；首次切换不顺便变更向量模型或索引。若生产启用了其他派生存储，也须纳入一致性核对，但不将其变成新的业务事实源。
- 配置显式选择 `local` 或 `distributed`。后者缺少数据库、对象存储或 Worker 必要配置时启动失败，不回落到本机数据。

这些边界以现有公开业务契约为接口约束，避免重写 RAG、问答、笔记和学习规则。当前 `app/session.py`、`app/runtime.py`、`app/coordination.py`、`app/storage.py`、`app/bootstrap.py` 中的进程／磁盘依赖均须在启用第二个 API 实例前消除或替换。

## 4. 实施与切换顺序

1. **基线冻结。** 固定当前业务镜像、SQLite／文件／Qdrant 配对备份及真实账号验收记录。隔离工作区开发分布式模式，保留生产单实例不变。已有独立工作树的未完成实现只按实际差异审查，不直接视为可合并成果。
2. **共享数据底座。** 接通 PostgreSQL schema 与事务、对象存储、会话及跨实例协调、独立 Worker，覆盖全部已上线业务所用权威状态。中间技术层可以单独验证，但不以其测试数量宣布迁移完成。
3. **隔离完整迁移。** 从同一停写边界取得的生产形态只读配对副本进行可重复、可核验的 SQLite／文件迁移；Qdrant 使用对应的隔离副本或快照，不连接生产写端。记录迁移清单、来源与目标哈希／数量、用户作用域、缺失项和恢复日志。失败保持隔离状态，不改生产。
4. **隔离业务与回退验收。** 在迁移后的环境、使用实际启用的依赖运行认证、导入、检索与引用、问答、来源笔记、学习任务、报告、删除与重启持久化；按实际启用的业务功能补齐路径。制造 API 与 Worker 故障、重复领取和租约过期，确认不串用户、不重复提交。开放隔离写入后，从候选分布式镜像切回独立构建并受验的分布式回退镜像，在同一 PostgreSQL／对象存储上读取并继续处理新写入。
5. **生产停写切换。** 进入受控维护，停止旧 Worker 与写入，制作 SQLite／文件／Qdrant 同一停写边界的备份并校验；按隔离演练运行离线迁移，核对完成后先以单 API 加独立 Worker 内部验收，再开放写入。旧数据只读保留观察，不作为切换后新数据的权威。
6. **观察后扩容。** 单实例稳定且回退演练证据仍适用于正式版本后，才增加 API／Worker 副本，验证跨实例会话、同用户串行、故障接管和外部状态一致性。生产扩容与首次生产数据迁移不在同一变更窗口完成。

## 5. 回退与灾难恢复语义

| 时点／故障 | 动作 | 数据保证 |
| --- | --- | --- |
| 新系统开放写入前，迁移或内部验收失败 | 保持维护；撤销候选环境，使用停写边界配对备份和旧镜像恢复原单机服务。 | 原权威仍是 SQLite／文件／Qdrant；通过备份一致性核对后恢复写入。 |
| 新系统开放写入后，候选应用版本回归 | 仅撤回应用镜像到已验证兼容的分布式回退版本；不退回 SQLite，不回滚 PostgreSQL 数据。 | 保留新写入；上线前须演练回退版本能读取、写入并处理切换后的数据。 |
| PostgreSQL、对象存储或 Qdrant 权威数据损坏 | 停写、隔离故障、按经验证的配对恢复点恢复或前向修复。 | 这是灾难恢复，不声称与应用版本回退相同，也不默认零数据损失。须测量并报告恢复点、耗时和跨存储差异。 |

**首次切换的硬门槛：** 当前 SQLite 版本不能作为开放新系统写入后的回退镜像。开放写入之前必须存在一个独立、已在迁移后及新增写入后验证的分布式回退镜像，并保持 schema、对象格式及任务状态的向后兼容；否则不得宣称“可回退”或开放写入。数据库变更采用兼容扩展、后续收缩，不能在同一切换窗口删除回退版本需要的字段。即使有回退镜像，共同的数据底座缺陷仍需要停写与灾难恢复／前向修复，不能靠换镜像解决。

PostgreSQL WAL／时间点恢复、对象版本和 Qdrant 快照分别提供恢复机制，不构成跨存储原子快照。维护停写边界、清单、哈希／数量核对与隔离恢复演练用于建立业务一致性；实际对象存储和 Qdrant 部署的版本／快照能力须在选型时验证。

## 6. 完成条件与停机门槛

以结果而非新增测试数衡量进度：

- 隔离环境完整迁移成功，迁移清单和用户／文档／任务／对象／向量核对无未解释差异；全部已上线核心业务可在迁移后运行，重启后仍可读取。
- 跨实例用户隔离、会话连续性、同用户写协调、Worker 失联恢复、旧租约写入拒绝得到故障演练证据。
- 切换前恢复旧系统、切换后保留新写入的应用镜像回退均在隔离环境通过；后者必须用真正不同且兼容的回退构建验证。
- 停写、迁移、核对、开放写入和回退各步有可审计状态与停止点；任何不一致、无受验回退镜像或核心业务失败都阻止生产切换。
- 生产切换后先验证单 API＋独立 Worker，扩容另作验收；不能以隔离演练代替生产实际业务验证。

本设计只确认顺序和验收边界，不授权在当前回合修改业务代码或执行正式迁移。下一步在书面规格经用户复核后，按此设计制定首个实施计划；计划应把“隔离环境完整业务迁移与回退”作为交付闭环，而非仅交付 PostgreSQL 配置或测试桩。
