# 多用户系统设计

## 目标

为智能文档学习助手增加本地多用户系统，使每个用户拥有相互隔离的文档库、学习笔记、问答历史、学习报告和记忆系统，并为以后迁移 PostgreSQL、对象存储、Qdrant 或 API 服务保留清晰边界。

第一版使用本地 SQLite 注册登录。用户名唯一，不做邮箱验证、密码找回、管理员或角色权限。

## 方案选择

采用混合隔离方案：

- SQLite 管理用户身份、报告索引和旧数据迁移状态。
- 每个用户以不可变 UUID 作为内部身份和数据目录名。
- 现有 RAG、学习历史和报告文件迁入用户专属目录。
- Gradio 前端状态只持有高熵随机会话令牌；服务端会话注册表持有身份和会话级 Assistant。
- 同一用户的多个会话共享一个用户 Runtime，其中集中管理 RAG、Memory、历史仓储和用户级锁。
- 存储路径由专门的用户存储服务生成，业务代码不直接拼接任意用户路径。

不采用仅用用户名拼 JSON 文件名的最小方案，因为它无法提供可靠身份认证，且用户名变更、路径安全和并发访问风险较高。暂不将全部 chunks、笔记和记忆关系化，因为这会在本阶段重写现有 RAG 持久化链路，超出实现多用户隔离所需范围。

## 架构边界

保持现有依赖方向：

```text
Gradio UI
  -> Authentication / Session Registry
  -> Session-scoped PDFLearningAssistant
  -> Shared User Runtime
  -> MemoryTool / RAGTool
  -> Memory / RAG / Storage
```

身份边界遵循以下规则：

1. 登录成功后生成至少 32 字节熵的随机会话令牌；Gradio `State` 只保存该令牌，不保存用户 UUID、密码或 Assistant。
2. 服务端进程内会话注册表将令牌映射到用户 UUID、用户名、会话级 Assistant 和最后访问时间。
3. 同一用户的多个 Assistant 只保存各自的当前文档，数据服务由该用户的共享 Runtime 提供。
4. 业务操作只能从服务端会话取得用户 UUID，不接受界面自行提交的 `user_id`。
5. 未登录、已退出或已过期会话不能访问上传、检索、问答、笔记、记忆、报告或删除操作。
6. 用户名仅用于登录和展示；数据归属始终使用不可变 UUID。
7. 所有数据读取、写入、下载和删除都必须重新应用当前用户作用域。

## 组件职责

### 认证服务

认证服务负责注册、登录和读取用户身份：

- 创建 UUID 用户标识。
- 校验用户名格式和唯一性。
- 使用标准库 `hashlib.scrypt` 和每个账户独立的 16 字节随机盐保存凭证，不保存明文密码。首版参数固定为 `n=16384`、`r=8`、`p=1`、`dklen=32`，编码中保存版本和参数以便以后升级。
- 登录失败统一返回“用户名或密码错误”，不泄露账户是否存在。
- 使用 SQLite 事务维护账户一致性。

第一版会话使用进程内注册表，不写入 SQLite，也不实现跨应用 JWT 或长期令牌。会话令牌使用 `secrets.token_urlsafe(32)` 生成，采用滑动空闲超时：连续 12 小时未访问即失效。每次事件调用和新登录时清理过期会话；注册表最多保留 128 个活动会话，达到上限时先清理过期会话，仍满则拒绝新登录而不驱逐活跃会话。退出登录立即删除令牌映射。

### 会话注册表与用户 Runtime

会话注册表负责令牌校验、过期清理和退出，不接收前端提供的用户 UUID。用户 Runtime 注册表按用户 UUID 缓存共享运行时，包含：

- 用户专属 RAG Pipeline 及显式 `cache_path`。
- 可持久化 Memory 仓储与 MemoryTool。
- 学习历史仓储。
- 报告服务。
- 一把可重入的用户级写锁和活动会话引用计数。

会话级 Assistant 只保存 `current_document_id` 等浏览器会话状态，并调用共享 Runtime。某用户最后一个会话退出或过期后，Runtime 在无进行中操作时释放；下次登录从持久化文件重建。该模型避免同一用户的多个 Pipeline 各自持有旧 chunks 并覆盖对方写入。

### 用户存储服务

用户存储服务将用户 UUID 映射到固定根目录，并提供受控的子路径。调用方不能提交任意用户目录，也不能通过 `..`、绝对路径或用户名越界访问其他用户数据。

建议目录结构：

```text
data/
├── app.db
├── legacy_backups/
└── users/
    └── <user_uuid>/
        ├── documents/
        ├── rag/rag_cache.json
        ├── history.json
        ├── memory/memories.json
        └── reports/
```

上传的原始文档复制到当前用户的 `documents/<document_uuid><validated_suffix>`。用户可见的原始文件名只存入元数据；内部文档 ID 使用 UUID，避免同名文件覆盖。扩展名必须来自支持格式白名单，不能直接使用上传文件提供的任意路径。

RAG Pipeline 必须显式接收当前用户的 `rag/rag_cache.json`，不能仅依赖 namespace 或当前默认的共享 `./knowledge_base/rag_cache`。JSON 文件在用户锁内序列化到同目录临时文件，刷新并关闭后使用 `os.replace()` 原子替换。工作区的 `data/`、迁移备份和报告产物必须加入 `.gitignore`，不得提交用户数据。

### Assistant 与工具层

`PDFLearningAssistant` 必须由经过认证的服务端会话创建。它持有会话自己的当前文档状态，并调用该用户的共享 Runtime，不再依赖固定的 `user123` 或模块级全局 Assistant。

RAG 操作保留 `document_id` 隔离，并增加不可绕过的用户作用域。文档新增、搜索、问答、总结、统计、删除和清空都只能作用于当前用户的数据。现有 PDF 页码、来源元数据和多格式导入能力继续保留。

学习笔记和问答历史写入当前用户的 `history.json`。每条问答明确保存 `document_id`，删除文档时按结构化字段清理，不再通过路径字符串包含关系猜测归属。

当前 MemoryManager 主要使用进程内集合，不能满足重启恢复要求。第一版增加用户级 Memory JSON 仓储：初始化 Runtime 时加载 `memory/memories.json` 并恢复受支持的记忆项；添加、删除、遗忘、整合和清空成功后在同一用户锁内保存快照。所有记忆元数据包含用户 UUID，加载时拒绝 UUID 不匹配的记录。搜索、统计、遗忘和清空必须同时受当前用户作用域约束。无法稳定序列化的感知原始对象不在第一版持久化范围内，现有学习助手默认启用的 working、episodic 和 semantic 记忆必须持久化。

### 报告服务

每次生成学习报告都会：

1. 从当前用户的文档、问答、笔记和记忆生成内容。
2. 将 Markdown 快照原子保存到当前用户的 `reports/<report_uuid>.md`。
3. 文件落盘成功后，在 SQLite 事务中保存报告 UUID、用户 UUID、标题、相对文件路径和生成时间；数据库登记失败时立即删除本次新文件。
4. 返回报告内容并刷新当前用户的报告历史。

每次明确点击“生成报告”创建一份新快照。Word 导出由用户选中的已保存快照即时生成，避免内容因学习数据变化而不一致，也不创建第二条报告记录。报告列表、查看和下载都按当前会话用户过滤。列表遇到索引存在但文件缺失时隐藏该记录并写入安全日志，不返回悬空下载路径。

## 数据模型

SQLite 至少包含以下表：

### `users`

- `id`：UUID 文本主键。
- `username`：规范化后的唯一用户名。
- `password_hash`：包含算法参数、随机盐和派生值的密码哈希。
- `status`：第一版为 `active`，保留禁用能力但不提供管理界面。
- `created_at`、`updated_at`：UTC 时间。

### `report_records`

- `id`：报告 UUID 主键。
- `user_id`：外键关联 `users.id`。
- `title`：报告标题。
- `relative_path`：相对于该用户目录的受控路径。
- `created_at`：UTC 时间。

### `data_migrations`

- `id`：迁移记录主键。
- `migration_key`：例如旧版 `user123` 数据集的稳定标识，具有唯一约束。
- `claimed_by_user_id`：认领用户 UUID。
- `status`：`in_progress`、`completed` 或 `failed`。
- `backup_path`：位于受控备份根目录下的相对路径。
- `manifest_path`：迁移前只读清单的相对路径。
- `skipped_summary`：无法安全归属或不受支持的数据摘要。
- `started_at`、`completed_at`、`error_summary`。

SQLite 开启外键约束。数据库写入使用事务，敏感错误不直接展示给用户。

## 注册、登录与退出流程

注册规则：

- 用户名去除首尾空白，经 Unicode NFKC 规范化后使用 `casefold()` 生成唯一性键；展示值保存规范化后的大小写。长度为 3～32 个字符，只允许 Unicode 字母、数字、下划线、连字符和点，且首尾必须是字母或数字。
- 密码长度为 8～128 个 Unicode 字符；不强制复杂字符组合。
- 重复用户名返回明确但不包含内部数据库信息的提示。
- 注册成功后可直接建立当前 Gradio 登录会话。

登录规则：

- 验证成功后取得或创建用户共享 Runtime，生成随机会话令牌，并创建会话级 Assistant。
- 验证失败统一返回“用户名或密码错误”。
- 不将密码、密码哈希或用户目录放入前端可编辑字段。

退出规则：

- 从服务端注册表删除会话令牌，释放 Assistant 和当前文档状态；最后一个会话退出后释放空闲的用户 Runtime。
- 返回注册登录视图。
- 退出不删除任何持久化数据。

## Gradio 会话与并发

现有模块级全局 `assistant = PDFLearningAssistant(user_id="user123")` 必须移除。每个 Gradio 浏览器会话通过 `gr.State` 只保存随机会话令牌。事件处理函数先让会话注册表验证令牌，再取得服务端 Assistant；任何来自组件值的用户 UUID 均被忽略。

不同用户写入不同目录。同一用户的多个浏览器会话共享一个 Runtime，因此只存在一份内存中的 RAG、Memory 和历史状态；所有变更在用户级可重入锁内完成并持久化，避免旧副本后写覆盖。耗时的 LLM 生成不持有写锁，只在读取上下文快照和提交结果时短暂加锁。SQLite 自身负责账户、报告索引和迁移记录的事务并发。

进程内用户锁满足第一版本地单进程 Gradio 部署。多进程或多节点部署时，应将这些 JSON 存储替换为支持并发事务的数据库或外部服务；该升级不属于第一版范围。

## 旧数据认领与迁移

旧数据不会自动归属任何新用户。当前可识别的旧数据位置包括 `memory_data/learning_history_user123.json`、`memory_data/memory.db`、共享上传目录、旧 RAG cache 和旧报告目录；迁移器只处理实际存在且格式可识别的项目。已登录用户可主动执行一次“认领旧数据”：

1. 只读扫描旧数据，生成包含文件类型、数量、大小和可归属状态的清单；认领界面先展示清单和跳过项，再由用户确认执行。
2. 检查稳定 `migration_key` 是否已被成功认领，并在 SQLite 事务中创建 `in_progress` 记录。
3. 将旧文件复制到带时间戳的 `legacy_backups/`，不修改原文件。
4. 在用户目录之外的专用 staging 目录转换文档、RAG cache、学习历史、可归属记忆和报告。
5. 为缺失或不安全的文档 ID 生成 UUID，并同步改写 chunks、问答和相关元数据中的 `document_id`。
6. 共享 `memory.db` 中只有明确带有旧用户标识且结构受支持的记录才可导入；无法证明归属的记录列入 `skipped_summary`，不能猜测归属。
7. 校验记录数量、JSON 可解析性、原始文档存在性和引用关系。
8. 在用户锁内将已校验 staging 内容合并到用户目录；目标冲突时保留现有用户数据，并为迁移项分配新 UUID。
9. 成功后标记 `completed` 并删除 staging；失败时删除 staging、保留用户原数据和备份，并标记 `failed`。

唯一迁移键和事务状态确保重复点击不会重复导入。已由其他用户完成认领时，后续用户不能再次认领。

## 删除语义

- 删除当前文档：只删除当前用户、目标 `document_id` 的原始文件、RAG chunks、文档历史和相关问答；学习笔记默认保留。
- 清空全部文档：只清空当前用户的文档、RAG 数据和问答历史；学习笔记、报告快照和账户保留。
- 清空笔记：只清空当前用户的学习笔记，不影响文档、问答、报告和其他用户。
- 删除报告：第一版不提供删除操作；报告历史只读并可下载。
- 删除账户：第一版不提供。

## 错误处理与安全要求

- 密码使用前述 `scrypt` 参数和独立随机盐，比较派生值时使用 `hmac.compare_digest()`。
- 任何路径在使用前都验证解析后的绝对路径位于当前用户根目录内。
- 下载文件通过报告记录或文档记录解析，不接受任意文件路径。
- 用户 A 提供用户 B 的 `document_id`、报告 ID 或文件名时，系统返回当前作用域内不存在，不泄露对象是否属于其他用户。
- JSON 损坏时停止相关写操作并给出可恢复提示，不静默覆盖损坏文件。
- 文件成功而数据库登记失败的跨存储操作必须执行补偿删除；读取时不得返回缺失文件对应的下载入口。
- 迁移和报告失败记录安全摘要，界面不显示密码信息、绝对数据目录或堆栈。

## 测试策略与验收标准

所有功能按测试驱动方式实现。核心验收包括：

1. 用户可注册、登录和退出；重复用户名被拒绝，数据库中不存在明文密码。
2. 两个用户上传同名文档后，文档列表、原始文件、RAG chunks 和检索结果完全隔离。
3. 用户 A 无法通过伪造用户 ID、文档 ID、报告 ID 或路径读取、下载或删除用户 B 的数据。
4. 笔记、问答、记忆、统计和报告只包含当前用户的数据。
5. 每次生成报告都会保存不可变 Markdown 快照和报告索引；所属用户可查看并导出 Word。
6. `gr.State` 不包含用户 UUID 或 Assistant；伪造、退出和过期令牌均无法调用业务操作；会话上限和清理策略按设计生效。
7. 多个浏览器会话不会共享当前文档；同一用户会话共享 Runtime，不同用户 Runtime 完全隔离。
8. 同一用户并发写入 RAG、历史和 Memory 时不丢失已成功提交的数据，耗时 LLM 调用不会长时间阻塞其他写操作。
9. 删除当前文档、清空全部文档和清空笔记符合既有删除语义，且不影响其他用户。
10. 旧数据认领前可审阅清单；只能成功认领一次；无法证明归属的数据被跳过；失败迁移可重试且不留下半成品。
11. 报告文件写入或数据库登记任一步骤失败时不产生可见孤儿记录；Word 导出使用选定快照。
12. 应用重启后账户、文档、问答、笔记、working/episodic/semantic 记忆和报告可恢复。
13. PDF、TXT、Markdown、DOCX 导入，PDF 页码引用、总结模式、报告导出等现有能力通过回归测试。

测试分层包括认证与存储单元测试、Assistant/Tool 集成测试、两个用户的端到端隔离测试，以及 Gradio 事件函数的会话状态测试。测试数据全部使用临时目录和临时 SQLite 数据库，不接触工作区中的真实运行数据。

## 范围外事项

第一版明确不包含：

- 邮箱验证、密码找回、管理员、角色和团队空间。
- OAuth、JWT、公开 API 和跨设备长期会话。
- 账户删除、报告删除和用户名修改界面。
- PostgreSQL、对象存储、Qdrant 或多节点部署。
- 对现有 RAG 算法、嵌入模型和报告内容进行无关重构。

这些能力可在现有用户 UUID、认证服务、用户存储服务和仓储边界之上后续扩展。
