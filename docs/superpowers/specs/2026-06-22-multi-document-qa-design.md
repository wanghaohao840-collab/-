# 多文档联合问答设计

## 1. 目标与范围

在不破坏现有单文档能力和 `document_id` 数据隔离的前提下，支持用户显式选择 1–10 篇已导入文档，并完成：

- 跨多个文档联合检索与问答；
- 跨多个文档对比分析；
- 跨多个文档联合总结。

用户选择一篇文档时，系统保持现有单文档体验。用户选择多篇文档时，查询范围严格限制在所选文档集合内。首版不提供命名、保存或共享“文档集合”的功能。

## 2. 交互设计

问答和检索区域使用多选文档组件，最多允许选择 10 篇文档。界面提供以下模式：

- 自动；
- 联合问答；
- 对比分析；
- 联合总结。

“自动”模式按问题关键词识别意图：

- 包含“对比、比较、区别、差异、异同、共同点”等表达时，进入对比分析；
- 包含“总结、概括、综述、主要内容、核心内容、全文”等表达时，进入联合总结；
- 其他问题进入联合问答。

手动指定模式时不再进行自动识别。上传或刷新文档后，问答与检索区域的多选项同步刷新。

多选仅定义查询范围，不改变删除语义。删除操作仍只允许针对一个明确的当前文档，避免将多选误解为批量删除。

## 3. 架构边界

保持现有单向依赖：

`UI → PDFLearningAssistant → RAGTool → RAGPipeline`

各层职责如下：

- UI：收集文档标签列表、问题和模式，展示答案与错误；
- Assistant：解析并校验文档选择、识别模式、调用工具、记录学习历史；
- RAG Tool：选择检索策略、构造上下文与模式化提示词、格式化答案来源；
- Pipeline：在指定文档 ID 集合内过滤、排序和抽样 chunk。

底层 chunk 与 JSON 缓存格式保持不变；已有知识库无需迁移。所有过滤仍基于每个 chunk 已保存的 `document_id`。

## 4. 接口设计

### 4.1 文档范围参数

Pipeline 和 RAG Tool 的相关接口新增：

```python
document_ids: Optional[list[str]] = None
```

旧参数 `document_id: Optional[str]` 保持可用。内部通过一个规范化函数转换为去重且保持输入顺序的文档 ID 列表：

- 仅传 `document_id`：转换为单元素列表；
- 仅传 `document_ids`：去空、去重并保序；
- 两者都未传：保持原接口允许的全知识库行为；
- 两者同时传：返回参数冲突错误，不隐式合并范围。

Assistant 的 `ask()` 和 `search()` 接收文档选择列表及模式。文档标签继续采用现有的 `文件名 | document_id` 格式，并由 Assistant 统一解析，避免 UI 直接依赖底层存储。

### 4.2 历史记录

新问答记录增加：

- `document_ids`；
- `document_names`；
- `mode`。

保留原有 `document` 字段，使旧数据和旧报告代码继续可读。读取历史时所有新增字段均按可选字段处理，不执行迁移。

## 5. 检索与生成策略

### 5.1 联合问答和联合检索

Pipeline 先严格过滤所选 `document_ids`，再统一计算相关度并返回全局 top-k。普通联合问答以相关性为主，不强制每篇文档都出现；未被选中的文档不得进入结果。

每条结果继续携带：

- 文件名；
- `document_id`；
- PDF 页码（如有）；
- 相关度分数；
- chunk 内容及原有 metadata。

### 5.2 对比分析

对每篇所选文档分别执行限定范围检索，为每篇文档保留基础证据配额，然后合并上下文。这样可避免高分文档吞掉全部名额。

提示词要求答案按以下结构组织：

1. 共同点；
2. 差异点；
3. 逐文档依据；
4. 信息缺失或无法比较之处。

如果某篇文档没有相关证据，答案必须标记“该文档未提供相关信息”，不得将缺失内容推断为差异。

### 5.3 联合总结

每篇文档调用按位置均衡抽样的总结上下文接口，从开头、中部和结尾抽取代表性 chunk。系统先形成带文档边界的逐文档上下文，再由一次综合生成输出：

1. 各文档摘要；
2. 跨文档共同主题；
3. 重要差异或互补信息；
4. 综合结论。

所选的每篇有效文档都必须在逐文档摘要中出现。某篇文档没有有效 chunk 时，明确列为缺失，不静默忽略。

## 6. 上下文与数量控制

- 一次选择至少 1 篇、最多 10 篇文档；
- 对比模式按文档分配检索条数，保证基础覆盖；
- 总结模式按文档分配采样与字符预算，保证整体上下文有界；
- 文档数量增加时优先压缩单篇上下文，而不是移除整篇文档；
- 重复选择同一文档只计算一次，并保持首次出现顺序。

具体配额保留为内部常量，初始值通过测试固定其覆盖语义，而不是把数值暴露为首版 UI 配置。

## 7. 来源与答案约束

生成提示词要求模型只能依据检索资料回答。上下文块包含明确的文档名、文档 ID 和页码标签，答案末尾输出实际参与生成的来源列表。

来源格式继续复用现有 `_format_source()` 逻辑，并确保多文档结果不会因页码相同而跨文档去重。去重键至少包含 `document_id` 与 `page_number`。

若所选范围内没有相关内容，返回明确的无结果信息，不退回全知识库检索，也不调用未选择文档。

## 8. 错误处理

以下情况在 Assistant 层提前返回用户可理解的错误：

- 未选择文档；
- 选择超过 10 篇；
- 标签无法解析出文档 ID；
- 模式不在允许值中；
- 问题或检索词为空。

Pipeline 对空 `document_ids` 视为显式空范围，不等同于“未指定范围”，防止意外检索全部文档。对比或总结中部分文档无结果时继续处理其他文档，并在输出中列出缺失文档。

## 9. 兼容性

- 现有 `current_document_id` 与单文档选择、删除流程继续保留；
- 现有调用仅传 `document_id` 时行为不变；
- 持久化 chunk 和缓存 JSON 不变；
- 旧问答历史缺少多文档字段时仍可展示；
- PDF、TXT、Markdown 和 DOCX 的来源信息继续沿用现有解析结果。

## 10. 测试策略

使用标准库 `unittest`，不新增测试依赖。测试按层覆盖：

### Pipeline

- 单 `document_id` 行为兼容；
- 多 `document_ids` 严格过滤；
- 未选中文档绝不进入结果；
- 空列表不扩大为全库；
- 多文档来源去重不串文档；
- 总结抽样覆盖每篇文档的不同位置。

### RAG Tool

- `document_id` 与 `document_ids` 冲突时报错；
- 联合问答使用全局相关结果；
- 对比模式为每篇文档取得证据；
- 联合总结包含每篇有效文档；
- 无结果和部分文档缺失时输出明确。

### Assistant

- 标签解析、去重和保序；
- 最少 1 篇、最多 10 篇限制；
- 自动识别三类模式；
- 手动模式覆盖自动识别；
- 历史记录包含文档集合和模式；
- 单文档调用保持可用。

### UI 辅助函数

- 多选值正确传入 Assistant；
- 上传和刷新后两个多选组件同步；
- 删除仍要求单个明确文档。

## 11. 验收标准

1. 用户可从已导入文档中选择 1–10 篇并提问或检索；
2. 联合检索结果只来自所选文档，且来源可追溯；
3. 对比分析覆盖每篇所选文档，并区分“内容不同”和“没有信息”；
4. 联合总结为每篇文档给出摘要，再输出跨文档综合；
5. 自动模式和手动覆盖均按设计工作；
6. 单文档问答、总结、检索和删除行为保持兼容；
7. 已有知识库与历史记录无需迁移即可继续使用；
8. 自动化测试覆盖范围过滤、模式分派、来源、错误边界和兼容路径。

## 12. 非目标

首版不实现：

- 保存或命名常用文档集合；
- 跨用户联合检索；
- 批量删除所选文档；
- 自动选择相关文档；
- 对文档集合进行独立持久化或权限管理；
- Qdrant 或 Neo4j 后端迁移。
