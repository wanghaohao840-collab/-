# 多文档联合问答设计

## 1. 目标与范围

在不破坏现有单文档能力和 `document_id` 数据隔离的前提下，支持用户显式选择 1–10 篇已导入文档，并完成：

- 跨多个文档联合检索与问答；
- 跨多个文档对比分析；
- 跨多个文档联合总结。

用户选择一篇文档时，系统保持现有单文档体验。用户选择多篇文档时，查询范围严格限制在所选文档集合内。首版不提供命名、保存或共享“文档集合”的功能。

## 2. 交互设计

问答和检索区域使用多选文档组件，最多允许选择 10 篇文档。界面提供以下模式：

- 自动；
- 联合问答；
- 对比分析；
- 联合总结。

“自动”模式按问题关键词识别意图：

- 包含“对比、比较、区别、差异、异同、共同点”等表达时，进入对比分析；
- 包含“总结、概括、综述、主要内容、核心内容、全文”等表达时，进入联合总结；
- 其他问题进入联合问答。

多个模式的关键词同时命中时，按“对比分析 > 联合总结 > 联合问答”的优先级选择。例如“对比两篇文档并总结共同点”进入对比分析，并可在对比答案中包含总结性结论。

对比分析至少需要 2 篇文档。无论模式来自自动识别还是手动指定，只选择 1 篇文档时都不静默降级，而是提示用户至少再选择一篇文档。手动指定其他模式时不再进行自动识别。上传或刷新文档后，问答与检索区域的多选项同步刷新。

多选仅定义查询范围，不改变删除语义。删除操作仍只允许针对一个明确的当前文档，避免将多选误解为批量删除。

## 3. 架构边界

保持现有单向依赖：

`UI → PDFLearningAssistant → RAGTool → RAGPipeline`

各层职责如下：

- UI：收集文档标签列表、问题和模式，展示答案与错误；
- Assistant：解析并校验文档选择、识别模式、调用工具、记录学习历史；
- RAG Tool：选择检索策略、编排分层总结、执行 prompt 预算、构造模式化提示词并格式化答案来源；
- Pipeline：在指定文档 ID 集合内过滤、排序和抽样 chunk。

底层 chunk 与 JSON 缓存格式保持不变；已有知识库无需迁移。所有过滤仍基于每个 chunk 已保存的 `document_id`。

## 4. 接口设计

### 4.1 文档范围参数

Pipeline 和 RAG Tool 的相关接口新增：

```python
document_ids: Optional[list[str]] = None
```

旧参数 `document_id: Optional[str]` 保持可用。内部通过一个规范化函数转换为去重且保持输入顺序的文档 ID 列表：

- 仅传 `document_id`：转换为单元素列表；
- 仅传非空 `document_ids`：去除空字符串、去重并保序；若规范化后为空，则视为显式空范围；
- 两者都未传：保持原接口允许的全知识库行为；
- 两者同时传：返回参数冲突错误，不隐式合并范围；
- `document_ids=None` 表示未传范围，`document_ids=[]` 或仅含空字符串的列表表示显式空范围，两者不得互相转换。

Assistant 的 `ask()` 和 `search()` 接收文档选择列表及模式，并保留基于 `current_document_id` 的旧单文档调用路径。文档标签继续采用现有的 `文件名 | document_id` 格式，并由 Assistant 统一解析，避免 UI 直接依赖底层存储。Assistant 在任何检索、历史写入或模式分派之前完成空范围、数量、模式、对比文档数量以及 `document_id`/`document_ids` 冲突校验；旧调用未显式传范围时才允许回退到 `current_document_id`，显式空列表不得触发该回退。RAG Tool 和 Pipeline 在各自公开入口保留相同的防御性冲突与空范围校验，以保护绕过 Assistant 的现有直接调用方。

### 4.2 历史记录

新问答记录增加：

- `document_ids`；
- `document_names`；
- `mode`。

保留原有 `document` 字段，使旧数据和旧报告代码继续可读。读取历史时所有新增字段均按可选字段处理，不执行持久化迁移。展示旧记录时按以下规则构造兼容视图：

- 有 `document_ids` 时直接使用；
- 缺少 `document_ids` 但存在旧 `document` 路径时，以 `Path(document).stem` 派生单元素 `document_ids`，以 `Path(document).name` 派生单元素 `document_names`；
- 两者都缺失时显示“未知文档”，不伪造文档 ID，也不回写原记录。

## 5. 检索与生成策略

### 5.1 联合问答和联合检索

Pipeline 先严格过滤所选 `document_ids`，再统一计算相关度并返回全局 top-k。普通联合问答以相关性为主，不强制每篇文档都出现；未被选中的文档不得进入结果。

每条结果继续携带：

- 文件名；
- `document_id`；
- PDF 页码（如有）；
- 相关度分数；
- chunk 内容及原有 metadata。

### 5.2 对比分析

对每篇所选文档分别执行限定范围检索，初始目标为每篇至少 2 个达到 `min_score` 的 chunk，然后合并上下文。该配额是相关证据的覆盖目标，不用低于阈值的无关 chunk 强行补足；不足 2 个时保留已有证据并标记该文档证据不足。这样可避免高分文档吞掉全部名额，同时不把低相关内容包装成依据。

提示词要求答案按以下结构组织：

1. 共同点；
2. 差异点；
3. 逐文档依据；
4. 信息缺失或无法比较之处。

如果某篇文档没有相关证据，答案必须标记“该文档未提供相关信息”，不得将缺失内容推断为差异。

### 5.3 联合总结

联合总结采用 map-reduce，而不是把所有原始 chunk 塞入一次调用：

1. Pipeline 为每篇文档按位置均衡抽样，优先保留开头、中部和结尾的代表性 chunk；
2. RAG Tool 对每篇文档分别生成受预算约束的单篇摘要；
3. 最多使用 3 路有界并发执行单篇摘要，避免 10 篇文档串行造成过长等待，也避免无限并发触发服务限流；
4. 所有单篇任务结束后，再用一次综合调用生成跨文档结果。

每个单篇任务返回结构化结果 `{document_id, document_name, summary, source_refs, status, error}`。`source_refs` 使用稳定的局部引用 ID 指向该任务实际使用的 chunk。综合调用接收“文档摘要 + 紧凑引用标签”，不接收原始 chunk 正文；最终来源列表取所有成功单篇任务 `source_refs` 的有序并集。因此分层总结不会丢失文件名、页码或截断状态。

最终输出结构为：

1. 各文档摘要；
2. 跨文档共同主题；
3. 重要差异或互补信息；
4. 综合结论。

联合总结中的“有效 chunk”定义为：`document_id` 匹配、已存在于当前知识库且正文去除空白后非空的 chunk。总结抽样不应用问题相关度阈值，因此“相关度低”不会使一个已成功索引的文档失效。

所选的每篇有效文档都必须在逐文档摘要中出现。缺失原因分开表达：

- 文档没有任何可用的非空 chunk：提示“文档没有可用的索引内容，可能尚未成功导入或索引已被删除”；当前缓存加载会丢弃空正文 chunk，因此首版不伪造“空正文索引”和“没有索引”的细分状态；
- 在联合问答或对比模式中有非空 chunk、但没有达到相关度阈值的结果：提示“文档中未找到与当前问题相关的内容”，属于内容相关性问题。

单篇摘要调用失败时记录该文档失败原因，不取消其他文档任务；综合结果列出失败文档，并只基于成功摘要生成共同主题和差异。所有文档都失败时不执行综合调用，直接返回失败汇总。缺失或失败文档不静默忽略。

## 6. 上下文与数量控制

首版使用以下内部配置和常量：

```python
LLM_CONTEXT_WINDOW_TOKENS = 8_192  # 可由环境变量覆盖
ANSWER_OUTPUT_TOKEN_RESERVE = 1_024
DOCUMENT_SUMMARY_OUTPUT_TOKEN_RESERVE = 384
TOKEN_SAFETY_MARGIN = 512
COMPARE_BASE_CHUNKS_PER_DOC = 2
COMPARE_EXTRA_CHUNKS_PER_DOC = 3
MIN_TRUNCATED_CHARS = 200
SUMMARY_MAX_WORKERS = 3
```

`HelloAgentsLLM` 提供统一的 `estimate_tokens(text)` 接口。存在匹配当前模型的 tokenizer 时使用实际计数器；没有时使用 `len(text)` 作为近似估算，并通过 `TOKEN_SAFETY_MARGIN` 降低特殊字符误差风险，不新增 tokenizer 依赖。近似估算不宣称等同于模型真实计数；若服务端仍返回上下文超限错误，RAG Tool 将其转换为明确的容量错误且不使用截断后的请求自动重试。配置必须满足 `context_window > output_reserve + safety_margin`，否则在调用模型前返回配置错误。

每次调用的最大输入预算为：

```text
input_budget = context_window - output_reserve - safety_margin
context_budget = input_budget - estimate_tokens(system_prompt + fixed_template + user_query)
```

预算覆盖完整输入，包括系统提示词、固定模板、用户问题、文档标签和资料正文。若固定内容本身已耗尽预算，直接返回“问题或提示词过长”，不调用模型。配额处理规则如下：

- 一次选择至少 1 篇、最多 10 篇文档；
- 对比模式先为每篇文档选择 2 个达标 chunk；每篇最多产生 3 个额外候选，额外候选先按文档内相关度排序，再汇总后按全局相关度从高到低加入；只有加入完整资料标签和正文后仍不超过本次 `context_budget` 时才接纳该额外 chunk；
- 组装后的估算 token 数仍超出预算时，先按全局相关度从低到高移除额外 chunk，再对其余 chunk 正文等比例截断；截断后的正文不得少于 `min(original_length, 200)` 个字符；
- 若某个 chunk 必须截到低于该下限才能满足预算，则整体移除该 chunk，不保留失去语义的几十字片段；移除按低相关度优先，并在同分时从当前拥有更多 chunk 的文档开始，尽量保持文档覆盖；
- 对比模式的基础证据在 200 字符下限之上均匀压缩；若完整资料标签加上所有基础证据的最小保留内容仍超过预算，则返回“所选范围超出当前模型容量，请减少文档”，不得静默删除某篇文档的基础证据；
- 单篇总结在自己的调用预算内先移除开头/中部/结尾锚点之外的抽样 chunk，再均匀压缩锚点正文；文档拥有对应位置时必须保留三个位置锚点，不能按虚构的相关度删除；
- 最终综合调用只接收单篇摘要及紧凑引用标签，不接收原始 chunk 正文；摘要超出综合预算时先均匀压缩每篇摘要，但每篇成功摘要至少保留 200 字符。若最小摘要集合仍超预算，则返回容量错误，不移除整篇文档；
- 重复选择同一文档只计算一次，并保持首次出现顺序。

预算处理只操作检索结果的浅层结构和复制后的正文，不修改 Pipeline 中的持久化 chunk。被截断但仍参与模型上下文的结果增加顶层运行时字段 `truncated=True`；被整体移除的 chunk 不进入模型上下文，也不进入实际参与生成的来源列表。以上常量通过测试固定其覆盖与压缩语义，不暴露为首版 UI 配置。

## 7. 来源与答案约束

生成提示词要求模型只能依据检索资料回答。上下文块包含明确的文档名、文档 ID 和页码标签，答案末尾输出实际参与生成的来源列表。

分层总结中的来源由 map 阶段实际使用的 chunk 决定，而不是由 reduce 阶段重新检索。reduce 阶段只能引用传入的稳定引用 ID；失败任务和预算处理中被整体移除的 chunk 不得出现在最终来源列表。

来源格式继续复用 `_format_source()` 的文件名、文档 ID 和页码逻辑，但接口扩展为 `_format_source(metadata, truncated=False)`；`truncated=True` 时追加“上下文已截断”。完整去重键为 `(document_id, normalized_page_number, content_digest)`：

- `normalized_page_number` 将缺失页码统一为 `None`，但不单独用于区分无页码 chunk；
- `content_digest` 在预算压缩之前，对未截断的完整正文进行 Unicode NFKC 规范化、统一换行为 `\n`、去除首尾空白，再对 UTF-8 字节计算完整的 64 字符十六进制 SHA-256；不截取正文前缀，也不截断哈希；
- 运行时去重始终使用上述内容摘要，不根据 `chunk_index`、顶层 `id` 或 `memory_id` 改变算法，因此新旧缓存混存时同一正文得到相同 identity；
- 同一文档同一页中规范化后完全相同的正文视为重复来源；不同正文即使前缀相同也不会合并；
- 因此 TXT、Markdown、DOCX 等无页码文档中的不同 chunk 不会退化为只按 `document_id` 合并。

处理顺序固定为“规范化范围 → 检索 → 对未截断原文计算摘要并去重 → 复制结果 → 预算压缩 → 构造 prompt 与来源”。截断不得改变 `content_digest`，运行时字段不得写回 JSON 缓存。

若所选范围内没有相关内容，返回明确的无结果信息，不退回全知识库检索，也不调用未选择文档。

## 8. 错误处理

以下用户输入问题在 Assistant 层提前返回可理解的错误：

- 未选择文档；
- 显式传入空 `document_ids`，或去空后没有有效 ID；
- 选择超过 10 篇；
- 标签无法解析出文档 ID；
- 模式不在允许值中；
- 同时传入 `document_id` 与 `document_ids`；
- 对比模式只选择了 1 篇文档；
- 问题或检索词为空。

以下模型与预算问题由掌握完整 prompt 的 RAG Tool 检测并返回：

- LLM 上下文窗口配置小于输出预留与安全余量之和；
- 固定提示词、用户问题或最小文档覆盖已经超出本次调用预算；
- 服务端实际 token 计数仍判定上下文超限。

Assistant 不会把显式空列表透传为有效查询。RAG Tool 与 Pipeline 仍将空 `document_ids` 视为显式空范围并返回参数错误，不等同于“未指定范围”，从而防止直接调用时意外检索全部文档。对比或总结中部分文档无结果时继续处理其他文档，并按第 5.3 节定义的原因分类列出缺失文档。

## 9. 兼容性

- 现有 `current_document_id` 与单文档选择、删除流程继续保留；
- 现有调用仅传 `document_id` 时行为不变；
- 持久化 chunk 和缓存 JSON 不变；
- token 预算配置未设置时使用 8,192 token 的保守默认窗口，现有 LLM 默认输出仍为 1,024 token；
- 旧问答历史缺少多文档字段时仍可展示；
- PDF、TXT、Markdown 和 DOCX 的来源信息继续沿用现有解析结果。

## 10. 测试策略

使用标准库 `unittest`，不新增测试依赖。测试按层覆盖：

### Pipeline

- 单 `document_id` 行为兼容；
- 多 `document_ids` 严格过滤；
- 未选中文档绝不进入结果；
- `None` 与显式空列表语义不同，空列表不扩大为全库；
- 多文档来源去重不串文档；
- 前缀相同但完整正文不同的 chunk 生成不同 `content_digest`；
- 新旧缓存的 `chunk_index`、`id`、`memory_id` 字段差异不影响相同正文的去重结果；
- 去重使用未截断原文并发生在预算压缩之前，截断不改变 `content_digest`；
- 总结抽样覆盖每篇文档的不同位置。

### RAG Tool

- `document_id` 与 `document_ids` 冲突在各公开边界报错；
- 联合问答使用全局相关结果；
- 对比模式以每篇 2 个达标 chunk 为基础配额，额外候选单篇不超过 3 个，并按全局相关度和估算 token 预算接纳；
- 完整 prompt 预算包含系统提示词、固定模板、问题、资料标签与正文，并为输出和估算误差预留空间；
- 精确 token 计数器与近似估算器均遵循同一预算接口，服务端上下文超限时返回容量错误；
- 验证先移除额外 chunk、再等比例截断基础 chunk 的预算压缩顺序；
- 基础证据在 200 字符下限仍无法容纳时返回容量错误，不移除某篇文档；
- chunk 需要截断到 200 字符以下时整体移除，不向模型传递失去语义的片段；
- 被截断 chunk 的来源带“上下文已截断”标记，被移除 chunk 不出现在来源中；
- 预算处理不修改 Pipeline 持有的 chunk 或缓存序列化结果；
- 联合总结对每篇文档保留位置锚点，以最多 3 路并发生成单篇摘要，再执行综合调用；
- 单篇摘要结构保留稳定引用 ID，综合调用后的来源等于成功任务实际来源的有序并集；
- 单篇摘要部分失败时其他任务和综合结果继续，全部失败时不执行综合调用；
- 10 篇成功摘要超出综合预算时均匀压缩，不能静默移除整篇摘要；
- 无可用索引内容与无相关结果两类可观测缺失原因输出明确。

### Assistant

- 标签解析、去重和保序；
- 最少 1 篇、最多 10 篇限制；
- 自动识别三类模式；
- 多关键词命中时按“对比 > 总结 > 问答”分派；
- 手动模式覆盖自动识别；
- 单文档对比返回数量提示，不静默降级；
- 历史记录包含文档集合和模式；
- 旧历史从 `document` 路径派生兼容展示字段；
- 单文档调用保持可用。

### UI 辅助函数

- 多选值正确传入 Assistant；
- 上传和刷新后两个多选组件同步；
- 删除仍要求单个明确文档。

## 11. 验收标准

1. 用户可从已导入文档中选择 1–10 篇并提问或检索；
2. 联合检索结果只来自所选文档，且来源可追溯；
3. 对比分析覆盖每篇所选文档，并区分“内容不同”和“没有信息”；
4. 联合总结为每篇文档给出摘要，再输出跨文档综合；
5. 自动模式和手动覆盖均按设计工作；
6. 单文档问答、总结、检索和删除行为保持兼容；
7. 已有知识库与历史记录无需迁移即可继续使用；
8. 自动化测试覆盖范围过滤、模式分派、来源、错误边界和兼容路径。

## 12. 非目标

首版不实现：

- 保存或命名常用文档集合；
- 跨用户联合检索；
- 批量删除所选文档；
- 自动选择相关文档；
- 对文档集合进行独立持久化或权限管理；
- Qdrant 或 Neo4j 后端迁移。
