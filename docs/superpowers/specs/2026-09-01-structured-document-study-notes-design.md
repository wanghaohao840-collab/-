# 文档结构化学习笔记设计

## 1. 目标

为当前智能文档学习助手增加“结构化学习笔记”能力。用户导入文档后，可以在所选文档范围内主动点击“生成学习笔记”，后台生成并持久保存一份适合学习和复习的只读笔记。

生成结果以固定阅读骨架组织，但根据文档类型和实际内容自适应栏目。技术教材可包含章前总览、逻辑链条、分节知识点、代码、注意事项和章节总结；论文或报告改用背景、方法、结果、结论和局限；没有代码的材料不得生成空代码栏目。

每个关键结论必须能回到原文核对。PDF 优先展示文件名和页码，其他格式展示文件名以及可用的章节或片段定位。

## 2. 当前实现基线

当前仓库已经具备：

- PDF、TXT、Markdown 和 DOCX 导入；
- 按 `document_id` 隔离的 RAG 检索、问答和总结；
- PDF 页码、来源片段和稳定引用 ID；
- 后台联合总结任务；
- 用户手写笔记、学习历史和报告；
- 本地多用户、会话和用户目录隔离；
- Gradio 运行入口。

当前“总结”是一次问答结果，当前“学习笔记”是用户手动录入内容。仓库没有按文档持久保存、具有稳定结构和生命周期的 AI 学习笔记。

仓库另有 React + FastAPI 产品化界面设计，但当前实际运行入口仍是 Gradio。本功能首版在 Gradio 中完成，服务边界必须允许未来 React 文档详情页直接复用。

## 3. 已确认的产品决策

1. 文档导入成功后不自动生成笔记。
2. 只有用户点击“生成学习笔记”才启动后台任务。
3. 一次任务只处理当前用户选择的一篇文档。
4. 输出采用“固定骨架 + 内容自适应”。
5. 笔记归属于单篇文档；未来 React 界面放在文档详情的“结构化笔记”页签。
6. 首版 Gradio 新增独立“结构化笔记”页签，作为文档详情页签的兼容表达。
7. AI 结构化笔记只读，允许重新生成；用户个人补充继续进入现有手写笔记模块。
8. 关键内容必须带原文来源定位。
9. 重新生成期间继续展示旧笔记；新任务成功后才替换当前版本。
10. 笔记任务失败不得影响文档导入、问答、检索和手写笔记。
11. 首版不同时实施 React + FastAPI 产品前端迁移。

## 4. 范围

### 4.1 首版包含

- 单篇文档结构化笔记生成；
- 后台任务的启动、查询、进度、取消、失败重试和重新生成；
- 持久化的任务状态与当前有效笔记；
- 固定骨架、文档类型自适应和引用校验；
- PDF 页码以及非 PDF 来源定位；
- Gradio 单文档选择、操作按钮、任务状态、Markdown 阅读区和来源展示；
- 文档更新后的过期提示；
- 文档删除、全部文档清空和应用重启的一致性处理；
- 用户隔离、文档隔离和回归测试。

### 4.2 首版不包含

- 自动生成；
- AI 笔记在线编辑；
- 多篇文档联合笔记；
- 笔记导出；
- 练习题、知识卡片或间隔复习；
- 完整目录解析器和人工章节边界编辑器；
- React 产品前端实现；
- Redis、Celery 或多进程任务队列。

## 5. 架构

依赖方向保持为：

```text
Gradio UI
  -> StructuredNoteService
  -> PDFLearningAssistant
  -> RAGTool
  -> RAG Pipeline / Storage / LLM
```

任务和结果持久化位于应用层：

```text
StructuredNoteService
  -> StructuredNoteTaskRepository
  -> DocumentNoteRepository
  -> application SQLite database
```

生成规则不放在 Gradio 事件处理函数中。Gradio 只负责认证入口、参数传递、状态格式化和组件更新。应用服务负责用户/文档校验、任务生命周期和持久化协调。Assistant 和 RAG Tool 负责文档范围内的证据获取与笔记生成。

## 6. 组件职责

### 6.1 `StructuredNoteService`

应用层公开入口，职责包括：

- 从会话令牌解析当前用户；
- 校验目标文档存在且属于当前用户；
- 启动首次生成或重新生成；
- 对同一 `user_id + document_id` 的活动任务做幂等控制；
- 查询、取消和重试任务；
- 读取当前有效笔记；
- 判断笔记是否因源文档变化而过期；
- 删除文档时协调任务取消和笔记删除；
- 应用启动时恢复中断任务为可重试状态。

服务不得持有未经仓储确认的任务真相。进程内 Future、线程和取消事件只是执行机制，SQLite 记录是对外状态来源。

### 6.2 `StructuredNoteTaskRepository`

负责结构化笔记任务的 SQLite 读写和状态转换。状态转换必须带当前状态条件，避免重复点击、轮询、取消和 Worker 完成回调互相覆盖。

允许的任务状态：

```text
queued -> running -> succeeded
queued -> cancelled
running -> cancelled
queued/running -> failed
failed/cancelled -> queued  (显式重试生成新尝试)
```

“重试”复用同一失败或取消任务记录，递增 `attempt_count` 后重新排队；“重新生成”只从已有成功笔记发起，并创建新的任务 UUID。已成功任务不重新排队。这样既保留单次任务的重试审计信息，也能明确区分不同笔记生成批次。

应用启动时遗留的 `running` 任务转换为 `failed`，错误代码使用稳定的可重试中断语义；不得继续显示为仍在执行。

### 6.3 `DocumentNoteRepository`

负责当前有效笔记的持久化读取、原子替换和删除。

重新生成时不得提前删除旧笔记。只有新结果完成结构和引用校验后，才能在一个数据库事务中：

1. 保存新笔记；
2. 将新笔记设为当前版本；
3. 将对应任务标记为 `succeeded`。

事务失败时旧笔记仍然有效，任务进入可诊断失败状态。

### 6.4 `PDFLearningAssistant`

增加单篇文档结构化笔记生成用例。它接收明确的 `document_id`、进度回调和取消事件，调用 RAG Tool，并返回经过验证的结构化结果。

该用例不写入现有 `history["notes"]`，避免把 AI 笔记混入用户手写笔记。生成行为也不计为普通问答历史；如需学习活动记录，只记录独立的 `structured_note_generation` 事件。

### 6.5 `RAGTool` 与生成器

RAG Tool 提供独立的结构化笔记生成动作，不通过普通问答模式伪装实现。它可以复用现有全文总结上下文、跨位置采样、上下文预算、引用格式化和 LLM 传输能力。

生成器职责包括：

- 获取单篇文档的覆盖性证据；
- 为每段证据分配稳定引用 ID；
- 根据文档类型选择允许的栏目；
- 使用固定骨架生成 Markdown；
- 校验必需标题、非空内容和引用 ID；
- 输出 Markdown 与结构化来源列表；
- 在各阶段报告进度并响应协作式取消。

生成器不得创造未出现在允许引用集合中的 ID。

## 7. 持久化模型

### 7.1 任务表

新增 `structured_note_tasks`：

| 字段 | 语义 |
|---|---|
| `id` | 任务 UUID |
| `user_id` | 当前用户 UUID |
| `document_id` | 单篇目标文档 |
| `source_import_task_id` | 任务启动时的源文档版本 |
| `status` | `queued/running/succeeded/failed/cancelled` |
| `stage` | `queued/evidence/generating/validating/persisting/completed/failed/cancelled` |
| `progress` | 0–100 |
| `attempt_count` | 总尝试次数 |
| `error_code` | 稳定、可判断是否可重试的错误码 |
| `error_summary` | 面向用户的脱敏摘要 |
| `cancel_requested` | 持久化取消意图 |
| `created_at` | 创建时间 |
| `started_at` | 开始时间 |
| `finished_at` | 结束时间 |
| `updated_at` | 最后更新时间 |

同一用户、同一文档只允许一个 `queued` 或 `running` 任务。使用 SQLite 部分唯一索引保证约束，而不是只依赖 UI 禁用按钮。

### 7.2 笔记表

新增 `structured_notes`：

| 字段 | 语义 |
|---|---|
| `id` | 笔记版本 UUID |
| `user_id` | 当前用户 UUID |
| `document_id` | 所属文档 |
| `generation_task_id` | 产生该版本的任务 |
| `source_import_task_id` | 生成时对应的源文档版本 |
| `content_markdown` | 只读 Markdown 内容 |
| `sources_json` | 经过验证的结构化来源 |
| `document_type` | 生成器采用的内容类型 |
| `prompt_version` | 提示模板版本 |
| `is_current` | 当前有效版本标记 |
| `created_at` | 生成时间 |

每个 `user_id + document_id` 最多一个 `is_current = 1` 的版本。首版可以保留历史版本用于安全原子切换，但 UI 只读取当前版本，不提供版本浏览。

`sources_json` 中每条来源至少包含：

```json
{
  "citation_id": "S-...",
  "document_id": "...",
  "file_name": "...",
  "page_number": 19,
  "section": null,
  "excerpt": "...",
  "reference": "..."
}
```

非 PDF 来源允许 `page_number` 为 `null`，但必须提供可用的 `section`、片段序号或原文摘录。

## 8. 生成流程

1. 用户在 Gradio “结构化笔记”页签选择一篇文档。
2. UI 调用 `StructuredNoteService.start()`。
3. 服务先认证，再按当前用户历史校验 `document_id`，读取最新 `import_task_id` 作为源版本。
4. 仓储以幂等方式创建任务；存在活动任务时返回该任务，不重复提交。
5. 后台 Worker 取得任务，将状态改为 `running/evidence`。
6. Assistant 让 RAG Tool 获取覆盖文档开头、中部、结尾和关键章节的证据。
7. 生成器按固定骨架和文档类型形成 Markdown。
8. 校验器检查标题结构、非空栏目、允许引用 ID 和关键结论引用覆盖。
9. 通过校验后，仓储原子保存新版本并切换当前版本。
10. UI 轮询任务状态；完成后加载当前笔记和结构化来源。

首次生成和重新生成都会创建新任务；只有失败或取消任务上的显式“重试”复用原任务记录。重复点击首次生成或重新生成按钮时，如果已经存在活动任务，服务返回该活动任务而不是创建第二个任务。

建议进度阶段：

| 阶段 | 进度范围 |
|---|---:|
| 排队 | 0–5 |
| 整理证据 | 5–35 |
| 生成内容 | 35–80 |
| 校验结构与引用 | 80–92 |
| 持久化 | 92–99 |
| 完成 | 100 |

进度必须单调不下降。没有真实工作量数据时只报告阶段边界，不伪造平滑进度。

## 9. 输出内容契约

所有文档类型共有：

1. 标题与文档元信息；
2. 总览；
3. 内容组织或逻辑链条；
4. 按主题或章节拆分的主体；
5. 总结；
6. 来源依据。

技术教材可增加：

- 学习目标；
- 核心概念；
- 代码或操作示例；
- 注意事项和常见错误；
- 技术方案对比。

论文和研究报告可改为：

- 研究背景与问题；
- 方法；
- 数据或实验；
- 主要结果；
- 结论与局限。

生成器不得为不适用的文档输出空栏目，也不得为了满足模板而虚构代码、实验或结论。

## 10. Gradio 首版界面

新增“结构化笔记”页签，包含：

- 单选文档下拉框；
- 刷新文档列表；
- “生成学习笔记”或“重新生成”主按钮；
- “取消任务”和“重试”辅助按钮；
- 当前任务状态、阶段、进度和脱敏错误；
- `gr.Markdown` 笔记阅读区；
- 来源定位区；
- “添加个人笔记”跳转提示或明确说明。

首版 Gradio 不伪装成完整文档详情路由，但术语、状态和服务契约必须与未来 React 文档详情页一致。

视觉要求：

- 使用项目既定松绿学术色板；
- 清晰区分标题、正文、代码、提醒和来源；
- 代码块可读，正文行宽和行高适合长内容；
- 来源可折叠或放在正文之后，避免压过主要内容；
- 排队、生成中、完成、失败、取消和过期不能只依赖颜色表达；
- 在 Gradio 能力范围内做产品化排版，但高保真 React 草图是后续产品界面质量标准，不是本次重建前端的承诺。

## 11. 重新生成、更新与删除

### 11.1 重新生成

- 旧笔记在新任务执行期间继续可读；
- 同一文档不得并发启动第二个活动任务；
- 新任务成功后原子替换当前版本；
- 新任务失败或取消时旧笔记不变；
- 重新生成不删除用户手写笔记。

### 11.2 文档更新

笔记记录生成时的 `source_import_task_id`。当前文档历史中的 `import_task_id` 与其不同时，UI 显示“源文档已更新，建议重新生成”。系统不得自动启动任务。

### 11.3 删除文档

删除当前文档时必须在同一用户范围内：

1. 请求取消活动结构化笔记任务；
2. 删除该文档的结构化笔记和任务记录；
3. 继续执行现有 RAG 文档、问答历史和文件清理；
4. 保留其他文档和用户手写笔记。

清空全部文档对每篇文档执行等价清理。清空手写笔记只影响 `history["notes"]`，不得删除结构化笔记。

## 12. 错误处理与安全

- 所有 UI 处理函数先认证，再读取任务或笔记。
- 服务端从会话解析 `user_id`；不得相信浏览器传入的用户标识。
- 读取、取消、重试和删除都必须同时按 `user_id + document_id` 过滤。
- 模型错误、路径、密钥和连接信息经过现有脱敏规则后才进入 `error_summary`。
- 文档不存在、来源容量不足、模型调用失败、取消和引用校验失败使用稳定错误码。
- 引用校验未通过或生成内容不完整时，不保存为当前笔记。
- 取消采用持久化 `cancel_requested` 加进程内取消事件；Worker 在证据、生成和持久化边界检查。
- 应用关闭时停止接收新任务并协作式结束 Worker；已提交但未完成的任务在下次启动转为可重试状态。

## 13. 测试设计

### 13.1 单元测试

- 任务模型、合法状态转换和部分唯一索引；
- 任务创建幂等与重复点击；
- 进度单调性；
- 笔记原子替换；
- 失败或取消保留旧笔记；
- 源版本过期判断；
- 输出结构自适应；
- 引用白名单、PDF 页码和非 PDF 定位；
- 错误脱敏；
- 用户和文档过滤。

### 13.2 服务与 Worker 测试

- 未登录、伪造会话和过期会话在仓储访问前被拒绝；
- 不允许为其他用户文档创建或读取任务；
- 首次生成、查询、取消、重试和重新生成；
- 应用重启将遗留运行任务恢复为可重试失败；
- 删除文档取消任务并清理结构化笔记；
- 清空手写笔记不影响结构化笔记；
- 生成失败不影响文档问答和检索。

### 13.3 UI 测试

- 页签控件、单文档选择和事件绑定；
- 登录校验；
- 空状态、生成中、完成、失败、取消和过期状态；
- Markdown 与来源渲染；
- 轮询在终态自动停止；
- 重新生成期间继续显示旧笔记。

### 13.4 集成与回归测试

- 上传文档、生成笔记、重启、重新登录后仍能读取；
- 两个用户使用同名文件时数据完全隔离；
- PDF 关键结论带正确页码；
- TXT、MD 和 DOCX 生成时使用可用来源定位；
- 删除单篇和清空全部文档不残留结构化笔记；
- 现有导入、问答、检索、联合总结、手写笔记、报告和用户隔离测试继续通过。

验证必须使用仓库 `venv`，并在 Windows 环境继续使用仓库内 `--basetemp` 规避系统临时目录权限问题。

## 14. 验收标准

1. 登录用户可以为自己的一篇已导入文档主动启动结构化笔记任务。
2. UI 显示真实阶段、单调进度、取消和可重试错误。
3. 完成结果持久保存，刷新、退出登录和应用重启后仍可读取。
4. 技术教材输出接近“总览 → 逻辑链条 → 分节知识点 → 示例/注意事项 → 总结”的阅读结构。
5. 不适用栏目被省略，不虚构代码、实验或结论。
6. 关键结论引用只能来自当前文档证据；PDF 来源显示页码。
7. 重新生成失败或取消不会破坏旧笔记。
8. 文档更新后显示过期提示，不自动重新生成。
9. 删除文档只清理对应结构化笔记，其他文档和手写笔记不受影响。
10. 不存在跨用户或跨文档读取、取消、重试和删除。
11. 现有功能回归测试通过。

## 15. 后续演进

未来 React + FastAPI 产品化阶段，将同一服务映射到文档详情的“结构化笔记”页签，并实现已确认的高保真阅读体验：固定目录、阅读型排版、代码高亮、折叠来源、生成状态和响应式布局。

后续可以独立评估：

- 章节目录解析与逐章生成；
- 历史版本浏览；
- Markdown 或 Word 导出；
- 从 AI 笔记创建个人笔记、知识卡片和练习题；
- 多文档联合学习笔记；
- 分布式任务执行。

这些能力不属于首版实现范围。
