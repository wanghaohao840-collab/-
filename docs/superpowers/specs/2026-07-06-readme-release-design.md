# README 与当前功能发布设计

## 目标

让根目录 `README.md` 成为当前仓库的可靠入口，准确说明已经实现的多用户、数据隔离、多文档问答、JSON/Qdrant RAG、Memory、报告、迁移恢复和测试能力，并将当前工作区内已确认的新功能统一提交到现有功能分支。

## 内容结构

README 按“快速理解 → 安装运行 → 功能使用 → 架构与数据 → 验证与路线图”的顺序组织：

1. 项目定位与已实现能力；
2. 支持格式及多文档问答模式；
3. 安装、环境变量、JSON/Qdrant 后端配置和启动方式；
4. 用户注册、文档导入、问答、检索、笔记、报告、迁移和恢复流程；
5. 分层架构、核心实现目录和用户数据布局；
6. 安全与数据隔离约束；
7. 测试命令、已实现状态和仍未完成的路线图。

## 准确性原则

- 以当前代码和测试为准，不沿用 README 中已经过时的“后续优化”描述。
- 将多用户登录、用户级数据隔离、多文档联合/对比/总结和 Qdrant 后端列为已实现。
- 将 Neo4j 标记为内存占位实现，不宣称已接入真实 Neo4j 服务。
- 只宣称 UI、存储白名单和 RAG 解析链路共同支持的文档格式；当前端到端格式为 PDF、TXT、MD 和 DOCX。
- 明确 JSON 与 Qdrant 不双写、不会自动互相迁移。

## 发布范围

本次提交包含用户确认的整个工作区：功能源码、测试、设计文档、任务包、仓库指令和更新后的 README。以下内容继续排除：

- `.env`、API Key、访问令牌；
- `data/`、`memory_data/`、运行缓存和数据库；
- 上传文档和生成报告；
- Python、pytest、IDE 和虚拟环境产物。

## 验证与发布

更新后先检查 README 的关键能力、路径和配置是否与源码一致，再运行完整 pytest 测试。测试通过后显式审查暂存内容，创建一个覆盖当前完整功能集的提交，并推送当前分支 `codex/multi-document-rag-query` 到 `origin`。不直接修改或强推 `main`，也不自动创建 PR。
